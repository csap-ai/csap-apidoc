# CSAP Apidoc 产品路线图(草案,待审核)

> 2026-11-17 起草。审定后:本文件进仓库,官网增加"路线图"页,README 链接到它。
> 原 `csap-apidoc-devtools/APIDOC开发工具产品路线图.md`(2025-10,含"商业化策略"和示例性的版本记录)由本文件取代。

## 1. 定位

**CSAP Apidoc 是一个多语言的运行时 API 文档框架。** 服务启动时直接从代码生成文档,按接口控制显示哪些字段,页内在线调试;同一份文档同时提供给人(文档页面)和 AI(MCP)。

三样东西跨语言共用,这是"多语言"成立的基础:

| 共用部分 | 内容 | 现状 |
|---|---|---|
| **文档协议** | `/csap/apidoc*` 接口的 JSON 结构 | Java 定义;Go 已逐字节兼容 |
| **规则格式** | `<Controller>-method-field.yaml`(请求参数、返回字段、校验规则) | Java 定义;Go 已兼容,可直接复用 Java 项目的文件 |
| **前端** | 文档页面 `csap-api.html`、后台 DevTools | 只写一份,各语言内嵌同一份构建产物 |

所以新增一门语言 = 实现"扫描代码 → 输出协议 → 读规则",前端、MCP、团队版自动可用。

## 2. 现状(2026-11-17)

| 产品 | 状态 |
|---|---|
| Java(Spring Boot 2.x / 3.x) | **1.1.1 已发布到 Maven Central**(1.1.0 是首个发布到 Central 的版本,但实际是 Java 17 字节码,建议升级到 1.1.1) |
| Go(gin、net/http) | 开发中:M1–M3 完成(文档生成、返回过滤、请求校验、YAML/SQL 规则热加载、多实例同步),尚未发布 |
| 文档页面 | 中英文;在线调试(环境、全局请求头、鉴权、历史与重放、命名快照),1.1.1 起随 jar 发布 |

1.1.x 仍有的缺口(1.2.0 解决):**单独使用开源版时,运行时的返回字段过滤和参数校验不执行**(执行代码在 2025-10 的整理中移到了 csap-framework 的 Web 层)。1.1.0 的空指针、旧版文档页面、`@EnableApidoc(type=YAML/JSON)` 未注册等问题已在 1.1.1 修复。

## 3. 版本规划

时间是建议值,请审核时确定。

### 1.1.1 — 补丁(已完成,2026-11-17 发布)

- 所有模块编译为 Java 11 字节码(1.1.0 实际是 Java 17 字节码)
- 只引入文档 starter 即可使用(修空指针)
- 文档页面按源码构建,发布流程自动构建前端,不再打进旧前端
- 修:缓存被 `?key=` 改坏、`flush` 无效、YAML/JSON 文档策略未注册(`type=SQL_LITE` 改为启动即报错)、SQLite 模板库缺失(改为首次使用自动建库)、Spring Boot 3 下 DevTools 代理不生效、默认 HTTP 方法记录错误、内置正则错误、Postman 导出问题
- 前端:配置导出明文泄露密钥(安全)、调试面板代理与超时设置不生效、网关聚合详情地址错误、分组/版本下拉是占位
- CI 真正执行测试;示例工程可以直接运行
- 官网 apidoc.csap.ai 上线

### 1.2.0 — 运行时能力补全(建议 2026-12)

- **返回字段过滤**、**请求参数校验**作为独立模块重新提供(不依赖 csap-framework),Spring Boot 2 / 3 都支持;校验支持"观察模式"(只记录不拦截)
- 文档页读取 `@DocGlobalHeader` / `@DocAuth`,在线调试自动预填请求头和鉴权
- 暗黑模式
- **Go 版 v0.1.0 发布**(M4 后台管理、修改记录与回滚;M5 net/http 适配、Postman 导出)

### 1.3.0 — 文档即 MCP(建议 2027 Q1)

让 AI 智能体直接"读懂并调用"你的接口,不用另写一层。

- **`csap-apidoc-mcp`**:独立的 MCP 服务(stdio 和 Streamable HTTP),指向任意一个(或多个)CSAP 服务的 `/csap/apidoc`,自动把每个接口转成 MCP 工具:工具名、说明、参数 JSON Schema 都来自文档;返回字段按规则过滤。因为读的是协议,Java、Go 以及以后的语言都能用。
- **内嵌 MCP 端点**:服务自身提供 `/csap/mcp`,开箱即用,不用单独部署。
- **控制**:哪些接口暴露给 AI(白名单/黑名单,复用规则文件)、鉴权透传、只读模式(默认只暴露 GET)、调用审计日志。
- **Agent Skill**:`csap-apidoc` 技能**首版已提供**(`skills/csap-apidoc/`,覆盖 Java 接入、注解、YAML 规则、排查字段不显示);1.3.0 加入通过 MCP 查询和调试接口的用法。技能随仓库维护、随版本更新。

说明:kyty-data-center 的 MCP 服务就是基于 `/csap/apidoc` 输出生成工具的,已证明可行;1.3.0 把它产品化、通用化。

### 1.4.0 — 设计与协作基础(建议 2027 Q2)

- **Mock 服务**(已有设计文档 M9.3):按文档生成模拟数据,前端可先行开发
- **JSON Schema 导入导出**
- **字段库与模板**:常用字段、校验规则做成模板复用(现有正则模板的扩展)
- **版本管理与变更追踪**:文档版本快照、版本之间的差异对比、破坏性变更检测(可在 CI 里拦截)
- **接口上下线管理**:基于现有 `ApiStatus`(开发中 / 完成 / 过时),在文档和 MCP 中体现

### 多语言

| 语言 | 计划 | 首批适配框架 |
|---|---|---|
| Java | 已发布 | Spring Boot 2.x / 3.x(Spring MVC) |
| Go | 1.2.0 同期发布 v0.1.0 | gin、net/http;echo、chi、fiber 随后 |
| Rust | 2027 上半年 | axum、actix-web |
| Python | 待定 | FastAPI |
| Node.js / TypeScript | 待定 | NestJS、Express |
| 其他(Kotlin、C#、PHP…) | 按社区需求 | — |

为了让各语言长期一致,1.3.0 前先发布两样东西:

- **协议规范**:`/csap/apidoc*` JSON 结构、规则 YAML 格式、过滤与校验语义的正式文档(现在是"以 Java 实现为准")。
- **一致性测试套件**:一组标准输入和期望输出(黄金样本),任何语言的实现跑通即视为兼容。Go 版已经用这种方式对齐了 Java。

### 团队版(建议 2027 Q2 起)

面向多服务、多成员的团队,把分散在各服务里的文档集中管理。

- **文档中心**:汇聚多个服务(不限语言)的文档,统一搜索、统一入口(现有网关聚合的升级版)
- **成员与权限**:组织、项目、角色;细粒度权限(谁能看哪些接口、谁能改规则)
- **协作**:规则修改走审批;修改记录、回滚;评论;变更通知(邮件、IM、Webhook)
- **版本管理与变更追踪**:跨服务的版本发布记录、破坏性变更告警
- **API 监控与分析**:调用量、错误率、慢接口(基于在线调试与 MCP 的调用数据,以及可选的服务端埋点)
- **AI 辅助**:AI 生成测试用例、根据代码变更建议文档更新、团队共享的 MCP 网关
- **SSO**:OIDC、LDAP

## 5. 需要你决定

1. **各版本时间**:上面是建议值。
2. **团队版的形态**:
   - A. 开源核心 + 团队版商业授权(自部署收费)
   - B. 团队版也开源,另提供付费的托管服务(SaaS)
   - C. 团队版完全开源,不做商业化
   这决定团队版代码放在哪个仓库、用什么协议。
3. **语言顺序**:Rust 之后先做 Python 还是 Node.js。
4. **MCP 的默认安全策略**:默认只暴露 GET,还是默认全部暴露、需要显式关闭。
5. **官网写到什么程度**:建议官网首页只介绍已发布的能力,"路线图"单独一页写规划中的内容,并标明"规划中"。

## 6. 原则

- 官网、README 只把**已发布**的功能当作功能介绍;规划中的内容只出现在路线图,明确标注。
- 每个版本发布前,文档按代码核对一遍。
- 各语言实现以协议规范和一致性测试为准,不以某一种语言的实现为准。
