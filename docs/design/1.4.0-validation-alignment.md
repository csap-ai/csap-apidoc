# 请求参数校验对齐(Java 以 Go 为准)

状态:约定草案,待审。结论已由用户定:**非必填字段没传值时不校验,传了值就校验**,以 Go(`csap-apidoc-go/validate/validate.go`)为准。本文逐条对齐“什么算传了值”,给出行为对照表、已知差异和黄金用例;Java 实现在约定确认后做。

## 1. 现状与目标

| | Java 1.2.0 ~ 1.3.0 | Go v0.2.0 | Java 1.4.0 目标 |
|---|---|---|---|
| 非必填、没传值 | 不校验 | 不校验 | 不校验 |
| 非必填、传了值(含 Pattern、NotEmpty 等规则) | **不校验**(非必填字段根本没有登记到运行时校验) | 校验 | **校验** |
| 必填 | 校验 | 校验 | 校验 |

Java 为什么不校验:文档生成时只有 `required` 的字段才会 `addRequestValidate`(`DefaultAbstractMethod` 两处),非必填字段连带它的规则(`@Pattern`、`@Size`、YAML 里写的 Pattern、NotEmpty……)都没登记。目标是让非必填字段的规则也登记,运行时按下面的“传了值”判定执行。

## 2. “传了值”的判定(以 Go 为准)

Go 的 `checkValue` 顺序,Java 须一致:

1. 值**传了**且声明了类型(Integer、Long、Double、Boolean)时先检查格式,错误返回 `Type`(码 400,“数据格式错误”)。
2. **非必填且没传** → 放行,**不看任何规则**。
3. 没有校验规则:必填且值为空(null、空串、空数组、空对象)→ `Required`(码默认 400,提示“不能为空”);否则放行。
4. 有校验规则:按 `level` 升序(同级保持书写顺序)逐条执行,第一条失败即返回;**有规则时不再套 Required**,由规则决定(必填 + 只有 Pattern + 没传 → 通过,因为 Pattern 对没传的值放行)。

### 2.1 各位置、各形态的值是否算“传了”

| 位置 | 形态 | 是否传了 | 说明 |
|---|---|---|---|
| QUERY | 没有这个参数 | 否 | |
| QUERY | `?p`(没有等号) | **是**,值为空串 | 与 `?p=` 同义 |
| QUERY | `?p=` | **是**,值为空串 | 空串是传了值,非必填的 Pattern、NotEmpty 会对它校验 |
| QUERY | `?p=x` | 是 | |
| QUERY | `?p=a&p=b` | 是,取第一个 | Java 差异见 4.1 |
| HEADER | 没带 | 否 | 头名不区分大小写 |
| HEADER | 带了且值为空 | 是,值为空串 | |
| PATH | 值非空 | 是 | 路径参数一定有值;为空视为没传 |
| FORM / FORM_DATA | 表单体里有 → 用表单的;否则看查询串 | 同 QUERY | |
| BODY(JSON) | 没有这个键 | 否 | |
| BODY(JSON) | 值为 `null` | **否** | 与没有这个键等价 |
| BODY(JSON) | `""` | **是** | 非必填 + Pattern(`^[0-9]+$`)会失败 |
| BODY(JSON) | `[]`、`{}` | 是 | 非必填 + NotEmpty 会失败 |
| BODY(JSON) | `0`、`false` | 是 | 都不是“空” |
| BODY(JSON) | 上级对象为 `null` 或不存在 | 否,且**不级联校验下级** | 必填的下级也不报错 |
| BODY(JSON) | 上级是数组 | 对每个元素分别判定 | 空数组没有元素,不校验 |
| BODY | 不是 JSON、超过 1MB、multipart | 整个请求体不校验 | 交给业务处理 |

### 2.2 各规则对“传了值”的判定

| 规则 | 通过条件 | 备注 |
|---|---|---|
| NotNull | 传了(非 null) | 空串、空数组算非 null,通过 |
| NotEmpty | 不是 null、空串、空数组、空对象 | `0`、`false` 通过 |
| NotBlank | 字符串去空白后非空;非字符串同 NotEmpty | Go 有该类型,Java 只能经注解提供 |
| Pattern | 没传 → 通过;传了 → 值的文本匹配正则 | 数字、布尔按文本匹配(`12` → `"12"`);支持 `PATTERN_nn` 内置名 |
| 必填且没规则 | 值非空(null、空串、空数组、空对象不通过) | 规则 `Required`,码取 `required-code`,默认 400 |

## 3. Java 实现要点(约定确认后做)

1. **登记**:`DefaultAbstractMethod` 的两处 `addRequestValidate`,条件由 `required` 改为 `required || 有校验规则`;登记时保留 `required` 的真实值(非必填为 false)。
2. **执行**:`Validate.ValidateField.validators`:`!required` 且值为 `null` → 直接返回(不看规则);其余按现有逻辑。Java 里“没传”就是 `null`(缺字段、`null`、Spring 把空串转成 `null` 的非字符串参数)。
3. **开关**:`csap.validation.optional-field-rules`,取值 `validate`(默认,新行为)/ `skip`(恢复 1.3.0 及以前:非必填字段一律不校验)。放在 `ValidationProperties`,与 `mode`、`tip-type` 同级。
4. **升级提示**:CHANGELOG `[Unreleased]` 写明这是**行为变化**,可能拦下原来能通过的请求(例如非必填字段上有 `@Pattern`,调用方一直传格式不对的值)。建议先 `csap.validation.mode=observe` 观察违规日志再切 `enforce`,或临时设 `optional-field-rules=skip`。
5. 注解规则:非必填字段上的 `@Pattern`、`@Size`、`@Min` 等同样在传了值时校验;`@NotNull`、`@NotBlank` 等“必须有值”的注解在**非必填 + 没传**时不触发(是否必填以 `required` 为准,与 Go 一致)。
6. 文档页(规则的“必填”标志)和运行时校验继续共用同一个 `required` 结果(规则 > `@ApiProperty.required`),不变。

## 4. 已知差异(对齐后仍存在,不收进黄金用例)

| # | 差异 | Java | Go | 处理 |
|---|---|---|---|---|
| D1 | 非 String 参数传空串(`?age=`) | Spring 绑定成 `null`,算没传 | 算传了空串,类型检查放行,规则(如 Min)会失败 | 记录在案;Java 拿不到原始文本 |
| D2 | 重复的查询参数 `?p=a&p=b` | String 参数得到 `a,b`;`List` 得到全部 | 只取第一个 | 记录在案 |
| D3 | Pattern 匹配方式 | `matcher.matches()` 全匹配 | `MatchString` 子串匹配 | 内置正则都带 `^$` 无差别;**用户写的不带锚点的正则结果不同**,待 go-db 决定是否改成全匹配 |
| D4 | 违规里的字段名 | 叶子字段名(`sku`) | 请求体用规则路径(`request.items.sku`),单值参数用参数名 | 黄金用例不比较字段名 |
| D5 | 类型错误(`age=abc`) | Spring 绑定异常,由异常处理器转成码 400 | `Type` 规则,码 400 | 黄金用例不含 |
| D6 | JSON 键的写法 | Jackson 命名策略 | 依次试原名、下划线、驼峰 | 记录在案 |
| D7 | 规则类型 | `NotNull`、`NotEmpty`、`Pattern`、注解 | 另有 `NotBlank`、`Min`、`Max`、`Length`、`Size`、`Enum`、自定义 | 黄金用例只用三种共有类型 + 只配必填 |
| D8 | multipart、非 JSON 体、超过 1MB | 按已绑定的对象校验 | 不校验请求体 | 记录在案 |

## 5. 黄金用例

数据文件:[`docs/conformance/validation-cases.json`](../conformance/validation-cases.json)(66 条),Java、Go 各写一个测试读它,结果必须一致。每个用例只有一个字段:

```json
{"id": "query-optional-pattern-empty-string",
 "desc": "非必填、传了空串(p=):算传了值,正则不匹配,失败",
 "field": {"in": "QUERY", "name": "p", "required": false,
           "rules": [{"type": "Pattern", "pattern": "^[0-9]+$", "code": "1002", "level": 1, "message": "必须是数字"}]},
 "request": {"query": "p="},
 "expect": {"ok": false, "rule": "Pattern", "code": "1002"}}
```

- `field.in`:`QUERY` / `HEADER` / `PATH` / `BODY`;`BODY` 用 `field.path`(相对请求体根,点号分隔,经过数组时对每个元素校验)。
- `request`:`query`(原始查询串)、`headers`(名 → 值,不在里面表示没带)、`pathParams`、`body`(任意 JSON)。
- `expect`:`{ok:true}` 或 `{ok:false, rule, code}`;只比较 `ok`、`rule`、`code`。`rule` 取 `NotNull`、`NotEmpty`、`Pattern`、`Required`。

覆盖:

| 分组 | 条数 | 主要内容 |
|---|---|---|
| query | 21 | 非必填(没传 / 合法 / 不合法 / `p=` / `?p`)× Pattern、NotEmpty、NotNull;必填 × NotEmpty、Pattern、只配必填;level 排序 |
| header | 5 | 非必填没带 / 带了(合法、不合法);必填没带 / 带了 |
| path | 3 | 合法、不合法、非必填标志下传了值也校验 |
| body | 37 | 键缺失 / null / `""` / 数字 / `[]` / `{}` / `0` / `false` × 非必填与必填 × Pattern、NotEmpty、NotNull、只配必填;数组元素、上级为 null / 缺失 / 空数组、嵌套对象 |

**已用 Go 验证**:这 66 条在当前 `csap-apidoc-go/validate` 上全部通过(用临时测试直接构造 `apidoc.Endpoint{Checks: …}` 调 `Validator.Check`,未提交到 Go 仓库),说明用例就是 Go 现有行为;Java 实现完成后要在同一份文件上全部通过。Go 一侧的测试由 go-db 接入。

## 6. 待定

- D3(Pattern 全匹配还是子串):建议 Go 改成与 Java 一致的全匹配,或在文档里写明“自定义正则请自带 `^$`”。
- 是否把 Java 的 `skip` 开关列为长期选项:建议保留一个大版本,1.5.0 评估移除。
